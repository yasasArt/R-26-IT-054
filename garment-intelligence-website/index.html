Domain

Computer vision and IoT for apparel production

The research applies camera-based machine learning and simple operator hardware to the points on an apparel line where information is still captured by hand.

Background

Garment factories still rely heavily on manual counting, visual inspection and manual measurement. These processes are slow, error-prone and give supervisors little real-time insight into the production line.

On a single line there are four separate manual checkpoints. Hourly piece counts at the sewing station are written on a clipboard. Good-versus-rework at quality checking, and garment style, colour and size at packing, are each judged by eye at a different station with no shared record. Rework and downtime are reported once a shift from operator memory, then retyped into spreadsheets.

The stakeholders are the sewing operator, quality checker, packing team, line supervisor, production and industrial-engineering manager, and plant IT.

Research problem

Production is still recorded by hand. Four manual checkpoints on every line leave no usable data, and existing analytics products cannot replace them without a server room.

0garments with a measured cycle time under the manual baseline
4disconnected manual checkpoints per line
1×per shift: rework and downtime recorded from memory
0shared records between quality, style, colour and size checks

Existing approaches and their limitations

ApproachLimitation on a sewing floor
Manual tally sheets and visual checksNo cycle time per garment; quality, style, colour and size never reach a shared record; reports retyped at shift end.
Web or cloud shop-floor analytics dashboardsNeed a server, a network link and factory IT to run them, which a sewing floor does not have.
Isolated vision prototypesEach has its own repository, environment, ports, model and database; merging the code destroys authorship and model provenance, and leaving them apart is not a product.
Frame-by-frame activity countingClassifying every frame as sewing also counts repair motion and unrelated scenes, so output is over-counted.

Research gap

  1. Shop-floor analytics assumes connectivity. A sewing floor needs an offline, installable application that runs on one PC.
  2. Vision components ship as isolated prototypes. No published approach keeps each component's code, model and data separately owned while delivering one product.
  3. Frame-wise counting over-counts. Nothing ties the count to what the operator is actually doing at that moment.

Aim and objectives

Main aim
To build an AI-powered vision system that tracks garments in real time across the sewing, quality-checking and packing areas of an apparel line, running offline on one PC.
Objectives
  1. Ship one offline desktop installer covering sewing, quality checking and packing.
  2. Preserve each member's frontend, backend, checkpoint and database as independently verifiable assets.
  3. Make every count evidence-based: a scene gate, a confirmed temporal transition and a hardware interlock, not a single frame.
  4. Keep the AI runtime behind an authenticated boundary the user interface cannot reach.
  5. Prove production readiness with automated policy tests and a reproducible release pipeline.
Expected contribution
A working, offline garment-tracking product in which each count, quality split, style, colour and size record comes from a trained model plus explicit evidence rules, with each research component still traceable to its owner.

01Basic component details

C1 · Sewing area

A Vision-Based Framework for Real-Time Garment Piece Counting and Sewing Cycle-Time Measurement

Dharmarathna P.W.A.N. · IT21255892

Introduction. A camera observes one sewing workstation. A YOLOv8n detector first confirms that a workstation is visible. Only then does a temporal MobileNetV3-Small classifier look at eight-frame clips and decide between SEWING and IDLE_SETUP. A garment is counted at each confirmed sewing-to-idle transition, and its cycle time is stored. The operator reports rework and downtime with buttons on an ESP32-C3 Bluetooth controller.

Main problem addressed. Hourly piece counts are tallied on paper and no garment has a measured cycle time. Counting from video frame by frame would also count repair motion. The component produces a trustworthy count and cycle time where rework, downtime, an invalid view or a lost controller never inflate or erase the count.

Importance to the project. It produces the line's output number; every other component is measured against it. It also set the platform foundations: the Electron security model, the authenticated Python service pattern and the release pipeline.

02–03Aim and objectives

Aim
Count finished pieces at the sewing station and time every cycle, from one camera and one button controller.
Objectives
  • Validate the scene before classifying the activity.
  • Count on a confirmed transition, never on a single frame.
  • Use a hardware interlock that pauses counting at source during rework, downtime and controller outages.
Contribution
The evidence-based counting rule: a scene gate, a confirmed temporal transition and a hardware interlock.
Related work
MobileNetV3, YOLOv8 (see Domain)

04Research methodology

Development followed a documented phased plan, each phase with its own guide and acceptance checklist: Phase 0 frozen product behaviour, Phase 1 Electron foundation, Phase 2 authenticated FastAPI integration, Phase 3 real AI camera integration, Phase 4 physical IoT controller, then production packaging.

flowchart LR
  CAM[Camera or validation video] --> Y[YOLOv8n workstation detector 640px]
  Y --> G{Workstation visible?}
  G -->|No| P[Pause and cancel pending cycle]
  G -->|Yes| M[Temporal MobileNetV3 8 frames 224px]
  M --> S[5-prediction smoothing, conf 0.55]
  S --> D{SEWING 2.0 s then IDLE_SETUP 0.6 s?}
  D -->|Yes, cooldown 3.0 s| C[(Piece event with cycle time)]
  ESP[ESP32-C3 buttons B C D] --> I[REWORK / DOWNTIME / RESET]
  I --> C
Datasets
Workstation detector: Roboflow Universe workstation-validation v3 (CC BY 4.0). Temporal classifier: labelled sewing-workstation video clips; the validation split holds 995 clips (302 IDLE_SETUP, 693 SEWING).
Preprocessing
Eight evenly sampled fresh frames per 1.5-second window, resized to 224 × 224, ImageNet normalisation. Classification runs only on frames where the workstation is verified.
Classifier design
TemporalMobileNetV3Small: shared MobileNetV3-Small backbone per frame, mean pooling across the 8 frame features, head 576 → 1024 → 2 with ReLU.
Training setup
Backbone learning rate 1e-4, classifier 3e-4, weight decay 1e-4, label smoothing 0.05, class weights, batch 8, cosine annealing, up to 30 epochs with early-stopping patience 7, seed 42; best checkpoint at epoch 5. Workstation detector: yolov8n.pt, 50 epochs, batch 8.
Counting rule
A garment counts only when a session is active, both models are loaded, the camera works, the workstation is visible, the controller is connected, the mode is NORMAL, SEWING is confirmed for 2.0 s, IDLE_SETUP then holds for 0.6 s, and the 3.0 s cooldown has passed.
Evaluation
Accuracy, macro and weighted F1, per-class precision and recall, confusion matrix; detector precision, recall and mAP; automated policy and API tests; factory acceptance run.
Ethics and data
Recordings stay on the local PC. The repository rules forbid shipping private customer footage in source archives.

C2 · Quality checking

Real-Time Good and Rework Garment Counting at the Quality Checking Workstation Using Detection, Multi-Object Tracking and Zone-Based Verdict Logic

Pathiraja H.P.M.H.D.S. · IT22627582

Introduction. A camera watches the quality-checking point. A YOLOv8n model trained on one class, Garment-Piece-Detection, finds each garment piece, and ByteTrack gives it a stable ID. The frame is divided by two horizontal lines and a centre band. A piece that passes through the middle zone and leaves upward is logged as Good; one that leaves downward is logged as Rework. Each piece is counted once.

Main problem addressed. Good versus rework is judged by eye with no record. The component counts both at inspection and keeps them grouped by session so a pass rate can be reported.

Importance to the project. It turns the output number into a quality number: how much of the line's output was actually sellable.

02–03Aim and objectives

Aim
Separate accepted garments from rework at the quality-checking workstation, in real time.
Objectives
  • Accept recorded video as well as a live camera, so an inspection can be audited.
  • Keep good and rework as two separate series, never netted into one figure.
  • Keep quality records in the component's own database.
Contribution
A per-session good and rework record with pass rate, from one camera.
Related work
YOLOv8, ByteTrack (see Domain)

C3 · Packing area

Real-Time Garment Style and Colour Detection Using Confidence-Gated YOLOv8 for Smart Apparel Manufacturing

Jayaweera M.P.Y.C. · IT22556370

Introduction. One overhead webcam watches the packing table. A capture engine learns the empty table, finds a garment by its difference from it, waits until the garment has settled with no hand over it, and then asks a four-class YOLOv8n model (SHIRT, T_SHIRT, TROUSER, SHORT) to name the style by voting across frames. Dominant colours are measured on the garment's own pixels. Each capture feeds packing targets, pace, efficiency and an overtime forecast.

Main problem addressed. Style and colour are checked by eye at packing with no record, so nobody can tell during the order whether it will finish on time.

Importance to the project. It says what was made, and whether the order will finish on time.

02–03Aim and objectives

Aim
Recognise garment style and colour from one overhead webcam and turn the count into a production decision.
Objectives
  • Run YOLOv8n on CPU, so an ordinary factory PC is enough (no GPU, no tags on garments).
  • Fix the capture gate rather than enlarge the model.
  • Trust agreement across frames over one confident frame.
Contribution
The finding that live accuracy depends on when and on which pixels the model is asked: an empty table is never classified, because the model is never called on it.
Related work
YOLOv8, GrabCut, YCrCb skin map, k-means (see Domain)

04Research methodology

flowchart LR
  A[Every frame] --> B[Differs from learned empty table?]
  B -->|No| W[Waiting for garment]
  B -->|Yes| C[Not moving, settled 0.3 s]
  C --> D[Hands or face cover at most 6%]
  D --> E[Tight crop classified at 640 px]
  E --> F{3 of 7 frames agree 80%, mean conf 0.60, lead 0.25}
  F -->|No| U[Style unclear]
  F -->|Yes| G[Colour from garment pixels]
  G --> H[(Capture saved)]
  H --> L[Locked until table empty 1.2 s]
Dataset
Roboflow "Style Detection" v6: 3,033 images, four styles. Every image is a close-up with one garment filling most of the picture.
Model training
Pretrained yolov8n.pt, 50 epochs, batch 16, 640 × 640, Ultralytics 8.4.115, trained 23 Aug 2026.
Garment finding
Colour difference from the learned empty table in CIE Lab (ΔE 14, lightness weight 0.6, auto-exposure shift removed), so shadows are not mistaken for a garment. Moving pixels and skin pixels are excluded.
Capture rule
Outline stable for 0.3 s (overlap 0.85 with the previous frame, 0.75 over 0.4 s); hands or face may cover at most 6 %. Vote over 3 frames in a window of 7 with 80 % agreement, mean confidence 0.60 and a 0.25 lead over the runner-up. Locked until the table has been empty for 1.2 s.
Colour extraction
Garment pixels only (table and skin excluded), Gaussian blur, k-means on Lab pixels (k up to 5), clusters above 1.5 % mapped to the nearest of 15 named colours; GrabCut as fallback.
Decision support
Effective hours = shift hours minus fixed breaks minus logged downtime. Pace, ETA, efficiency and suggested overtime per target; next-day forecast from a weighted moving average blended with trend.
Evaluation
Test-set mAP, precision and recall; replay of recorded packing videos (replay_style_video.py); bench trial; automated component tests.

The line runs at 84.3 pieces per hour against the 122.9 it needs, so the order would finish nine days late. The system suggests about four hours of overtime a day.

Discussion

The model itself was not the problem: it scores mAP 0.958 on its test set. The earlier live loop asked it the wrong question, at the wrong moment, on pixels that included the table. In the saved history from that loop, 12 of 107 captures had the wrong style for those reasons, while clean, still, tightly cropped garments were correct in 101 of 106 cases. Moving the fix into the capture gate removed the systematic errors without changing the model.

Limitations

  • Closed class set with no background class, so an untrained garment is forced into one of four styles. Loose black trousers are read as SHIRT because the training trousers are mostly straight jeans.
  • Colour-naming accuracy and field accuracy are not yet measured.

Future improvements

  • Add a background class.
  • Report per-class F1.

C4 · Packing area

Real-Time Best-Frame Selection and Marker-Free Garment Size Measurement for Smart Apparel Packing

Jayarathna W.G.U.C.G. · IT22187796

Introduction. A camera fixed 100 cm above the table, pointing straight down, sees a garment laid flat. A YOLOv8n segmentation model outlines it, the outline is refined and straightened, and garment-specific measurements are converted from pixels to centimetres with a stored scale of 13.6 px/cm. The nearest size-chart entry gives the size, and each confirmed garment is counted against a production order.

Main problem addressed. Size is judged by hand at packing. The component measures instead, without a reference marker in every image, and counts sizes against an order's targets.

Importance to the project. It completes the packing record: which box, against which per-size target.

02–03Aim and objectives

Aim
Measure garments at a fixed height without markers and classify them to a production size.
Objectives
  • Choose the best frame by agreement between frames, not by sharpness.
  • Measure first and classify second, so size rules can change without retraining.
  • Keep orders in SQLite and count a garment only after it is removed.
Contribution
Marker-free measurement at a calibrated height with agreement-based best-frame selection.
Related work
YOLOv8 segmentation, GrabCut (see Domain)

04Research methodology

flowchart LR
  A[Frame 1920x1080 at 100 cm] --> B[ROI, 4% margins]
  B --> C[Low-contrast enhancement]
  C --> D[YOLOv8n-seg mask]
  D --> E[Best mask: area 4-50%, near centre]
  E --> F[GrabCut refinement]
  F --> G[Deskew and crop]
  G --> H[Width and length in px]
  H --> I[cm at 13.6 px/cm]
  I --> J{Nearest size within 8 cm?}
  J -->|Yes| K[Size label]
  J -->|No| L[UNKNOWN]
  K --> M[3 frames agree, then count]
Dataset
Garment segmentation dataset garment_seg_100cm_clean_v5, captured at the 100 cm installation height.
Model training
Pretrained yolov8n-seg.pt, up to 100 epochs with patience 15 (stopped after 34), batch 2, 640 × 640, seed 42, Ultralytics 8.4.116, trained 27 Aug 2026.
Calibration
Fixed height 100 cm, 90° to the table, zoom 1.0×, Logitech C922 at 1920 × 1080, 13.6 px/cm, no runtime marker.
Measurement rules
T-shirt and shirt: width straight across the body below both sleeves, length from centre collar to centre hem. Trouser: flat waistband width and outside-seam length.
Size matching
Euclidean distance to each chart size in cm (shirts weight width 0.7 and length 0.3); rejected as UNKNOWN beyond 8 cm.
Best frame
3 frames must agree (width within ± 1.5 cm, length within ± 2.0 cm); 3 empty frames plus a visible scene change re-arm for the next garment.
Evaluation
Box and mask precision, recall and mAP; platform and database tests.

Challenges and how they were addressed

ChallengeResolution
Dark garments scored low confidence.Low inference threshold (0.25; 0.15 for shirts) with geometry and temporal checks deciding the count.
Table regions leaked into masks.The YOLO mask seeds a GrabCut refinement; if refinement is unreliable the original mask is kept.
The same garment was counted twice after a missed frame.Re-arming needs empty frames and a measurable scene change.
Sidebar buttons did not respond inside Electron (v3.0).v3.1 marks the size sidebar as no-drag and scopes its styles.
Old order data leaked into new orders.Orders moved from browser storage to SQLite with validated dates, shifts and breaks, fresh forms, reset and protected delete.

Discussion

Mask mAP50-95 of 0.956 means garment outlines are tight even at strict overlap thresholds, which matters because every centimetre is computed from the mask.

Limitations

  • Moving the camera invalidates every measurement until it is recalibrated.
  • Measurement error in millimetres against a tape measure is not yet quantified.
  • Three garment types; sizes follow one fixed chart.

Future improvements

  • Quantify measurement error against tape-measured garments.
  • Configurable size charts per customer.

Security and data rules

  • Renderer has no Node access; context isolation and sandboxing are on.
  • Only named IPC methods and exact route/method pairs are allowed.
  • Backends listen on 127.0.0.1 only and never call each other.
  • Trained models are read-only; each feature writes to its own user-data folder.
  • Switching cards stops the outgoing camera first.
  • Release builds bundle each backend as a PyInstaller sidecar and record model SHA-256 checksums.
